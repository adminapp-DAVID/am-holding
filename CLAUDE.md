# AM Holding — guía para Claude

App React (Vite + Tailwind CSS v4 + base de shadcn/ui) de gestión financiera de la holding (AM SPORTS GROUP SAS, PRO INVESTMENTS GLOBAL SAS, PRONOVA CAPITAL SAS, FOR SEVEN MEDIA SAS, ARKO). Casi todo el código está en `src/App.js`. Backend: Supabase (Postgres + Auth + Storage, RLS activo). Deploy: Vercel automático en cada push a `main`.

## Estilo de respuesta

- Respuestas en español, muy concisas. Pocas preguntas aclaratorias, directas.

## Flujo de despliegue (obligatorio)

- **Por defecto: PR.** Todo cambio de lógica, datos, permisos/roles, Supabase/RLS, cálculos, soportes o formularios va en una rama + Pull Request. El usuario aprueba y hace el merge.
- **Push directo a `main`: solo cambios pequeños de UI/visuales** (textos, colores, estilos, posición o apariencia de botones) que no cambien el comportamiento. Avisar al usuario cada vez que se haga.
- Si hay duda sobre si un cambio es "solo visual", va por PR.
- Antes de subir, correr `npm run lint`, `npm test` y `npm run build` (los tres deben pasar sin errores ni warnings).

## Notas técnicas clave

- Sistema de diseño (shadcn/ui, migración por etapas): Tailwind se carga SIN preflight para no alterar los estilos en línea existentes. Tokens de la paleta AM Holding en `src/index.css` (`--primary` dorado, `--background` crema…). Componentes nuevos en `src/components/ui/` (shadcn, JS sin TypeScript, alias `@/`), utilidad `cn` en `src/lib/utils.js`. Etapa 2: ya existen Button, Input, Textarea, Select (nativo), Label, Card, Badge (`estadoBadge`), Table y Dialog (Radix); catálogo en `/sistema-diseno.html`. Sin preflight, cada componente fija borde/fuente/márgenes explícitamente. Variables de entorno siguen con prefijo `REACT_APP_` (leídas con `import.meta.env`).

- Roles (`20261113_roles_permisos.sql`, `src/permisos.js`, `RolesPermisosView.jsx`): tabla `public.roles` (codigo = usuarios.rol, nombre visible, rol_base, permisos jsonb por módulo). La seguridad usa el ROL BASE: Administrador, Coordinadora Administrativa (se muestra "Coordinación Administrativa"), Gerente, Contadora, Responsable (se muestra "Colaborador"). `current_rol()` y `user.rol` = rol base; `user.rolNombre` = nombre visible. La matriz solo baja niveles (ninguno < ver < editar < aprobar), nunca pasa `MAXIMO_POR_BASE`; canEdit/canApprove/isReadOnly siguen el nivel del módulo abierto. Permisos vía `canApprove`, `canEdit`, `isReadOnly`, `puedeEditarSolicitud(s)`.
- Supabase: un `.update()`/`.delete()` sin `.select()` devuelve `error: null` aunque RLS bloquee el cambio (0 filas). Usar `.select('id')` y verificar `data.length`.
- En SQL/RLS usar `current_usuario_id()` / `current_rol()`. **Nunca** comparar `auth.uid()` contra `usuarios.id` (el vínculo es `usuarios.auth_user_id`).
- Soportes: bucket `soportes` + tabla `public.soportes` (sin columna mime; se infiere con `inferirMimePorExtension`). Un mismo `bucket_path` puede estar compartido entre entidades: borrar/fusionar con `eliminarSoportesDeEntidad` y `fusionarSoportesEdicion`.
- Liquidaciones (`20261105_liquidaciones.sql`, `src/liquidaciones.js`, `LiquidacionesView.jsx`, `pagarLiquidacion` en App.js): colaborador + empresa que paga + mes; ítems con la misma clave que los lotes PAB (`solicitud:<id>`, `presupuesto:<id>:<año>-<mes>`, `ajuste:<uuid>`) e índice único sobre los activos (ni otra liquidación ni un lote PAB los toma: `liquidacionPorClave`). Estados Borrador → En revisión → Aprobada → Pagada / Anulada. Al pagar: un movimiento por concepto (solicitudes vía `handleChangeEstado`, presupuesto con bruto − deducciones, ajustes como gasto o ingreso) con el comprobante enlazado; re-ejecutable.
- Deducciones (`20261106_deduccion_aplicaciones.sql`, `src/deducciones.js`, `DeduccionHistorial.jsx`): historial real en `deduccion_aplicaciones`. Las cuotas las crea un trigger en `gastos` (Gasto con `presupuesto_item_id` y `deduccion_aplicada` > 0; las retenciones de terceros no tienen `presupuesto_item_id`); abonos/condonaciones/ajustes son manuales (Admin/Coord). Saldo real = saldo_total − aplicaciones. Si la tabla no carga, `cuotaEnMes`/`saldoPendienteEnMes` usan el cálculo por calendario.
- Operación Financiera Noss (OFN; `20261115_operacion_financiera_noss.sql`, `src/ofn.js`, `OperacionFinancieraNoss.jsx`, Edge Function `integracion-noss`): solicitud con `ofn` jsonb (proceso, jugadores, clubes con %) = gasto de AM SPORTS GROUP SAS; necesita `ofn_aprobacion = 'Aprobada'` de Gerencia Noss (solo la escribe `ofn_decidir()` vía integracion-noss) antes de Aprobado/Pagado/Legalizado (trigger `ofn_solicitud_control`; editar el contenido la vuelve a Pendiente). Listas de Noss en `noss_catalogo`. El gasto generado hereda `gastos.ofn`. Etapa 3 (`20261117_ofn_eventos.sql`): `ofn.evento` opcional (Proyecto/Viaje/Competencia de Noss, `noss_catalogo.tipo = 'evento'`); al pagar una solicitud OFN, `programarSincronizacionNoss` llama `integracion-noss` → `sincronizar`, que manda a Noss la lista COMPLETA de gastos con OFN (Noss: `ofn_movimientos` + Gasto real del evento); Noss también la pide con la acción `movimientos`. Etapa 4 (`20261119_ofn_servicios.sql`): `noss_catalogo.extra` + tipo `servicio`; cada jugador de la OFN puede llevar `servicio_id`/`servicio_nombre` (servicio de su plan de acompañamiento en Noss, planeado vs. real). El catálogo se lee con `select('*')`. Secretos: `INTEGRACION_AM_CLAVE` (igual en Noss) y `NOSS_INTEGRACION_URL`.
- Traslados a empresa externa usan el sentinel `CUENTA_DESTINO_EXTERNA = 'Empresa Externa'` (sin ":" para no activar la lógica de doble moneda).
- Seguridad: nunca automatizar login a portales bancarios con credenciales guardadas.
